## Scientific question

Does an executable synthetic **two-of-three Ed25519 witness receipt policy**, with a persistent verifier checkpoint ledger and explicit mock provider-effect IDs, handle witness outages, delays, conflicting signed heads and issuer/source rollback more safely than EXP-24's single local witness?

**Prediction:** two distinct valid witness receipts permit confirmation; one or invalid receipts yield `UNCONFIRMED_QUORUM`, not a success assertion. Forked source histories are detected by independent signed witness opinions if both are available. A separately supplied mock provider effects list of identical count but different IDs/tasks is rejected.

## Implementation and executed tests

`protocol.py`: an Ed25519 issuer key, three separate Ed25519 witness keypairs and SQLite receipt databases, a pinned verifier SQLite database, canonical JSON SHA-256 checkpoint hash over exact effect ID→task pairs, and per-witness signed receipts. Witness code refuses a signed alternate checkpoint at a previously accepted sequence; verifier requires two **distinct pinned witness identities** with valid signatures. The verifier persists sequence/head and rejects missing history and conflicting pinned source. A separate reconciliation function compares **specific effect IDs and task mappings**, rather than trusting event counts alone.

## Interpretations

| Observation | What is and is not supported |
|---|---|
| 2 of 3 witness receipts | Deterministic signed quorum acceptance. **Not** distributed consensus or Byzantine fault tolerance |
| Witness unavailable or only one receipt | `UNCONFIRMED_QUORUM`, not silent promotion |
| Valid issuer-signed conflicting checkpoint | Individual witness refuses a fork; independently signed conflicting heads may expose equivocation to a collector |
| Source missing after verifier pins head | `SOURCE_ROLLBACK` reported against persisted verifier |
| Mock provider set same count but wrong IDs/tasks | `PROVIDER_MISMATCH`, stronger than EXP-24 single count |
| Authorized signer produces false claim | Signature/quorum **do not establish real-world truth**, correctly exposed by negative control |
| Test operator replaces witness roots and databases | New fictional history can appear consistent; absence of independently pinned roots remains critical |

## Security and scientific limitations

1. All issuer/witness keypairs are generated by, and all four SQLite ledgers and verifier pinned trust roots controlled by, **one local test process**. Witnesses have distinct cryptographic keys but **not separate organizational custody, Linux principal isolation, host failure domains or remote persistence**. Rewriting everything defeats the local experiment.
2. `2-of-3` is a demonstration threshold, not a deployed consensus algorithm, fault-tolerance proof or guarantee of globally consistent history. Witnesses can disagree; a collector needs an authenticated gossip/pinned-key protocol.
3. The verifier authenticates pinned witness identities and their signed receipt of a checkpoint, but the source issuer's private key is held by the same test runner. Witnesses validate issuer signature on issuance, not independently verified provider truth.
4. The mock authoritative provider effect set is passed as input to reconciliation by the same test process. It is not a live provider readback, separately authenticated effect database or crash recovery from remote effects.
5. Delayed receipt arrival is modeled sequentially, without actual queue/network partition, expiry windows, retries, cancellation, late data retention or disaster recovery.
6. No source-bound independent QA, key rotation/revocation, secure role bootstrapping, signer compromise, real transparency log, delegated project identity, cost accounting or commercial customer assurance.
7. Passing negative control tests means **the bypass or false record was reproduced**, not that the system is secure.
