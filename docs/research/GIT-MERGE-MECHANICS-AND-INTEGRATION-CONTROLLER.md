# Git Merge Mechanics and the Integration Controller — Research Appendix

**Status:** Research clarification; not implemented. **Scope:** Foromni only.  
**Companions:** CONVERGENCE-CONTRACT-V0.1.md and CROSS-DOMAIN-CONVERGENCE-CONTRACT-V0.2.md.

## Why this appendix exists

The convergence contract must distinguish **who requests a contribution**, **who verifies it**, **what Git actually does**, and **who is authorized to publish it on main**. Merging is ordinarily not copying files between folders. Git combines commit histories and tree changes; depending on chosen strategy, the resulting mainline may point to the submitted commit, a new merge commit, a rebased/squashed commit, or an integration commit generated by a merge queue.

## Typical flow

1. **Branch:** Worker creates a short-lived branch from a known main commit and authors one scoped change.
2. **Commit and push:** Worker sends its commits to its own authorized remote ref. Independent workers should not indiscriminately push to a shared candidate ref.
3. **Pull request:** Worker proposes changing the destination ref; it is not yet an admission decision. The proposal records task/revision, source commit, dependencies, and acceptance claims.
4. **Pre-merge QA:** Trusted checks verify the candidate, including code review, permissions, dependency compatibility, CI, and relevant domain acceptance evidence. A successful local check does not suffice.
5. **Prospective combination:** A protected integration service, merge queue, or reviewer assembles the *would-be* result against current main and preceding eligible candidates. New test evidence must bind to that combination.
6. **Admission:** Authorized merge controller confirms approvals and that evidence still applies to the exact candidate and target state. If main/source/dependencies have changed, re-evaluate.
7. **Git merge/publish:** The hosting service applies its approved merge mechanism to the repository, updates the protected main ref, and records its actual new commit. No manual file-copy step is normally needed.
8. **Post-merge confirmation:** Read back main and actual SHA, validate integrated behavior, update task ledger, and separate later deployment/feature enablement from code admission.
9. **Cleanup/recovery:** Delete the obsolete work branch if appropriate (preserving commit/PR provenance); record rejections, conflicts, retries and supersession instead of silently erasing work.

## What Git combines

- **Fast-forward:** main ref advances to a descendant commit; no separate merge commit.
- **Merge commit:** Git records two parent histories and a new combined tree; conflicts may require authorized resolution.
- **Squash merge:** candidate changes become a new mainline commit; the new SHA differs from source SHA, so evidence/provenance must link them.
- **Rebase and merge:** candidate commits are replayed on a new base, producing new commit IDs; previous tests may not certify the actual integrated result.
- **Merge queue:** a service constructs speculative combinations and tests them before coordinating publication. Required checks need to run on the queue's merge-group revision.

**Critical:** A conflict-free textual merge can still break APIs, database assumptions, permissions or behavior. The contract must test functional compatibility, not merely whether Git computed a tree.

## Responsible roles

| Role | Allowed work | Not automatically authorized |
|---|---|---|
| Contributor/worker | Commit to own task branch; open PR; supply artifacts and evidence | Merge protected main or self-certify acceptance |
| Maintainer/code owner | Review source quality/design; approve within policy | Override independent security or required checks |
| Independent QA | Reproduce acceptance tests and issue scoped verdicts | Grant their own repository write rights |
| Integration controller | Verify latest eligible combination; perform policy-governed merge under narrowly scoped privileges | Release to production or approve unverified changes |
| Release owner | Approve rollout/publication when its criteria are met | Change history of prior QA or attribution |

The merge controller may be an approved human, a service/bot, or both. Git does not require a human to manually copy code; protected branch rules and checks determine whether a merge can proceed.

## Four synchronization pitfalls

1. Two workers read branch head A; first pushes B, second submits C built on A. Normal non-fast-forward protection rejects the second divergent push. A worker must preserve its contribution, fetch, reconcile, rerun checks and propose again.
2. A PR passed on SHA S but a new commit S2 is pushed; checks tied to S may no longer establish S2.
3. A PR passed against main M1 but main advances to M2; tests may need a new prospective merge-group result to be applicable.
4. A queue admits commit G, but roadmap ledger records S (source) as final integrated SHA. Correct attribution requires both source and **actual mainline SHA**, plus the admission decision and result verification.

## Convergence Contract evidence fields

To support real merge mechanics rather than a conceptual copy operation, require a *software domain adapter* to bind:

- task ID and task acceptance revision;
- PR/candidate identity and contributor actor;
- source repository/ref and source commit SHA;
- target repository/ref and expected base SHA;
- merge method, dependency set and prospective merge-group SHA;
- required status checks and their exact tested SHAs;
- independent verifier and gate policy revision;
- admission decision ID and authorized merge principal;
- actual integrated mainline SHA and post-merge checks;
- deployment/release decision separately, if any.

For non-code domains, replace Git-specific fields with equivalent versioned artifacts and domain-specific authority/evidence, without implying that a single Git repository controls the collective.

## Research-only checks

- Trace a PR through fast-forward, merge-commit, squash and rebase cases, checking SHA lineage.
- Trigger a stale-source and stale-base scenario with synthetic commits and confirm fail-closed admission.
- Confirm protected main denies direct agent writes and force pushes.
- Confirm any queue test runs on the actual speculative merge-group revision.
- Simulate successful merge followed by ledger failure; reconcile from actual mainline history without merging twice.
- Confirm a conflict-free merge that breaks a shared contract remains unaccepted or returns to repair.
- Confirm source branch cleanup cannot erase accepted contribution attribution.
