# E0 v0.5 Adversarial Contract Review — Findings and Corrective Recommendations

**Status:** Internal skeptical *paper* review of research proposals, **not independent external review, approval, implementation or security testing**.
**Date:** 2026-11-21 · **Scope:** Foromni only. No Internet Embassy systems or data.
**Reviewed:** FULL-STACK-COLLECTIVE-LAB-UNIFIED-CONTRACT-V0.4-REVIEW-CANDIDATE.md, FULL-STACK-COLLECTIVE-LAB-V0.5-DECISION-RESOLUTION-CANDIDATE.md, E0-V0.5-EVALUATOR-TRUST-BOUNDARY-AND-GRADE-ORACLE.md, E0-GITHUB-PROTECTIONS-READ-ONLY-REALITY-AUDIT.md.
**Method:** Read the actual branch versions, check scope and observed assertions for contradictions, attackable ambiguities and non-reproducible requirements. Findings below identify **specification gaps**, not vulnerabilities observed in running software. No testing occurred.

## Executive result

The v0.5 decision matrix resolves all fifteen open v0.4 decision slots at the **proposal** level but is **not yet a single self-contained executable contract**. Several specifications either remain incomplete or conflict with the evaluator's assumptions. Mark independent contract freeze **BLOCKED**, not “15/15 done.” The highest-information next task is a focused v0.6 review candidate with explicit end-to-end fixture/auth route, concurrency, pagination and test-environment behavior, submitted for independent review.

## 1. Findings (severity = risk to experimental interpretability)

| ID | Severity | Source of ambiguity | Why it matters | Recommended repair |
|---|---|---|---|---|
| **E0-R01** | Blocker | D-14 demands sign-in, logout, expiration and CSRF tests, but v0.4/v0.5 route roster defines **no login/logout/session creation/revocation endpoint**. | Two implementations could use entirely different invisible test hooks. A QA suite cannot reproduce sessions without a defined interface. | Specify test-only session bootstrap and logout/revocation paths (never live user accounts) OR define evaluator-owned auth transport adapter with exact documented input/output. Choose one and pin it for both arms. |
| **E0-R02** | Blocker | v0.5 D-14 says unsafe methods require “same-origin + CSRF token **or** same-origin Origin validation”; null/missing Origin is not decided. | Allows different security posture across trial arms and an untestable negative oracle. | Choose ONE behavior for browser requests, explicit origin/null/absence matrix, CSRF threat model and test transport. Require reviewer sign-off and positive/negative cases. |
| **E0-R03** | Blocker | D-02 proposes evaluator-controlled clock, while D-14 session expiry and D-08 invitation expiry rely on it; no secure boundary controls test clock. | A worker could influence time if the clock hook leaks into app interface; expiry assertions could be manipulated. | Clock injected only by independent test harness at process boundary; no remotely writable time endpoint; define exactly which components receive it and reset between cases. |
| **E0-R04** | High | D-09 says invitation accepted once, subsequent same-user attempt 409, token stored hashed, and expired recipient 410; status of consumed/expired token may be visible to holder. | Realistic threat model needs token non-disclosure rules, recipient authorization ordering, hash lookup and rate/control assumptions. | Use uniform non-disclosing 404 for invalid/wrong-recipient tokens; explicitly define known-recipient consumed/expired paths if returning 409/410. Review against information leak and timing. |
| **E0-R05** | High | D-05 says signed opaque cursor tied to viewer/scope/revision; changes to membership/visibility during pagination unspecified. | A cursor could continue revealing a now-private row or yield duplicates/non-deterministic omission. | Freeze recheck-on-every-page, cursor version/expiry, listing snapshot policy and handling when a project becomes private mid-pagination. |
| **E0-R06** | High | D-03 and D-10 exclude project-delete and member-role-change endpoints but v0.4 role matrix still lists them as supported owner operations. | A test author may call missing routes and unfairly mark implementations failed; or workers implement more than required. | Publish **E0 implemented-capability matrix** separate from future permission policy; explicitly mark these deferred and require only safe unsupported-method behavior. |
| **E0-R07** | High | v0.5 D-08 invites `manager` role; D-09 returns `member:{userId,role}`; no rule says what happens when target already belongs to project or invite is revoked/recipient deleted mid-flight. | Concurrent or duplicate memberships and privilege changes might be inconsistent across implementations. | Define allowed recipient state, unique(project,user) constraint, revoked/expired single-use transitions and transaction boundary. |
| **E0-R08** | High | Entity ETags `"vN"` are proposed per-entity without describing whether version is scoped to current representation or actor projection. | A public/private projection can differ while sharing ETag; conditional requests can be incorrectly compared; 409 vs HTTP 412 is a deliberate nonstandard choice. | Treat write-precondition as versioned mutable resource state, not a public caching validator; define returned ETag for authorized forms only and exactly what a 409 means. |
| **E0-R09** | High | v0.5 v0.4 “project description” and public projection overlap, while a project can transition private→public. | Accidentally private descriptions could be published; unclear if description is meant entirely public in public project state. | State that published project's title/description are explicitly public by owner choice and security fixtures test full projection before/after visibility change. |
| **E0-R10** | High | v0.5 D-15 keyboard essential flows name invites; v0.5 omits user sign-in UI and unclear whether an invitation recipient can be switched in browser fixtures. | UI acceptance differs based on invented routes/test harness. | Define limited user journeys and evaluator provisioned identities; remove untestable vague UI behaviors. |
| **E0-R11** | High | E0 evaluator allows ‘separate principal’ but does not specify how agent-controlled repositories, Docker sockets, files or secrets are isolated in a trial. | A worker could influence evaluator fixtures or host resources; separation is purely verbal. | Write a threat-boundary allocation table for worker vs evaluator hosts, storage, credential sources, network and result publication. Do not claim actual isolation until observed. |
| **E0-R12** | High | Candidate SHA vs checked source vs prospective merge SHA logic is specified, but no candidate-only clean-checkout method or merge-commit generation method is selected. | Uncommitted content or different dependency installation can be graded as if it were the claimed Git SHA. | Independent evaluator obtains its own checkout from observed Git ref, verifies clean state, exact lockfile/environment and records digest. Prospective-merge acceptance requires separate source snapshot, not inferred. |
| **E0-R13** | Medium | “Unicode code points” trimming, null descriptions, and unknown-field rejections unspecified for normalization and JSON duplicate keys. | Different stacks can disagree on 160-character boundary and accept ambiguous payload. | Define NFC/no-NFC behavior, whitespace trimming, duplicate JSON key rejection, 1–160 scalar-count validation, and allowed description update semantics. |
| **E0-R14** | Medium | Default 20/max 50 and `createdAt DESC,id DESC` but page parameter errors, hidden filtered rows and concurrent inserts are not precisely declared. | A candidate can pass simple pages while violating stable pagination. | Freeze nonpositive/noninteger `limit` errors, continuation keyset rule and tested snapshot/live-list semantics. |
| **E0-R15** | Medium | No explicit `PATCH project` empty-body no-op vs version increment, and partial successful audit transaction not specified. | Inconsistent audit/cost counts and stale versions. | Reject empty patch 422; each successful state-changing mutation increments version once and writes one audit event in same transaction; failed writes have no success event. |
| **E0-R16** | Medium | D-15 “zero critical/blocker accessibility failures” lacks reproducible severity criteria and permitted browser extensions/config. | Reviewer subjectivity can swing outcome; control/treatment may see unequal acceptance. | Define observable assertions (focus, submit, escape, labeled field errors, no horizontal overflow), pin browser flags and classify criticality before trials. |
| **E0-R17** | Medium | Evidence categories `SECURITY_BLOCKED`, `NO_TEST_EXECUTION`, `STALE_EVIDENCE` etc. can overlap. | Multiple evaluators may assign different terminal grades, corrupting outcome denominator. | Define precedence/primary grade + orthogonal reason tags, preserving all failure evidence. |
| **E0-R18** | High | GitHub main was observed unprotected and detailed protection API unavailable. | A proposed independent protected merger is not a verified host-enforced boundary. | Keep E0 isolated and candidate-only; no autonomous merge to main until admin audit and actual enforcement verification under separate approval. |
| **E0-R19** | Medium | E0 efficiency claims lack an exact cost reconciliation plan for tool retries, model billing, evaluator, human work and missing data. | False economic gains possible by excluding work done by planner/QA. | Preregister all-cost denominator, missing-cost policy and paired-control baseline after reproducible E0a. |
| **E0-R20** | Medium | Synthetic failure/attack prompts in README/PR require trusted Git permission denial, but E0 candidate may only use local patch artifact and have no broker tool at all. | A test could be meaningless (“safe because tool absent”) or require unauthorized live Git calls. | Separate non-executable policy-unit scenario from bounded end-to-end tool-denial scenario. Define what is actually within an authorized E0a scope before claiming PI-resistance. |

## 2. Recommended resolution order (not approval)

**Phase A — Contract completeness:** R01/R02/R03/R06/R07/R08/R10/R13/R14/R15. Write a canonical endpoint+fixture+auth adapter with explicit error/precondition tables; flag undecidable choices to reviewer.

**Phase B — Reviewer isolation:** R11/R12/R17/R18/R20. Identify which controls need a separate trusted host, Git policy, source observer or test harness, and which checks are only hypothetical.

**Phase C — Experimental validity:** R04/R05/R09/R16/R19. Document privacy/cursor/accessibility semantics and complete costs, with prespecified per-trial comparison policy.

Avoid expanding E0 into a broad social network, workforce admin dashboard, extra agent communication protocol or standalone monitoring infrastructure.

## 3. Independent reviewer acceptance checklist

A genuinely independent reviewer must explicitly record:
1. All fifteen D-01..D-15 decisions as APPROVE/REVISE/REJECT with rationale and reviewed source SHA;
2. A disposition for R01..R20 and whether any high/blocker findings remain;
3. The complete reference app endpoint/role/error matrix, synthetic auth/session test interface, deterministic time and fixture definition;
4. Independent evaluator identity/credential/data isolation and exact candidate SHA verification plan;
5. A documented no-main-automerge source-control boundary because current main is not visibly protected;
6. Full-cost/evaluation denominator, trial horizon and missing/ambiguous evidence handling;
7. Separate scoped founder authorization specifying whether to implement or execute anything. A paper sign-off alone is not authorization to spend, run workers, merge, deploy or contact others.

**No self-certification:** This paper review was produced within the same research workflow as the draft specification, so it is an *adversarial desk review*, not an independent QA verdict.
