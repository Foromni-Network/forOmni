## 2. Three different kinds of E0 blockers

### A. Contract blockers: resolvable by real reviewer decisions

- Auth/session choice and accepted CSRF/origin matrix (REV-A).
- Invitation privacy and end-of-lifetime behavior (REV-C).
- Cursor expiration/midstream permission mutation and ETag handling (REV-D).
- Complete grader conflict/precedence policy and case coverage (REV-E).
- Exact scope exclusions and whether login UI belongs in the required frontend (REV-A/B).

**Exit:** One reviewer-approved version-pinned contract and independent test-case registry. No agent author alone can satisfy this gate.

### B. Operational blockers: require executable/host evidence, not more prose

- Isolated worker with no evaluator secret, privileged host socket, production database or main-write token.
- Independent evaluator under truly distinct authenticated principal and separate results/holdout store.
- Clean evaluator-owned checkout at actual Git SHA, fixed package/browser/image and deterministic synthetic database/clock.
- Source-host permissions: API observed **Foromni main protected=false, required checks off**; no host-enforced main-merge claims until an admin reviews and configures protections with separate permission.
- Verified negative fixtures for task permissions, invitation race, authentication expiration, prompt injection and false-green grading.

**Exit:** Authorized configuration + executable evidence under scoped trial. Do not count research reports or GitHub comment approvals as runtime proof.

### C. Governance blockers: founder controls

- Exact named disposable repo, worker/model, network/data permissions, cost cap, maximum retries, stop conditions, reviewer, and teardown owner.
- Whether a benchmark run may perform any GitHub writes, unit tests or browser tests (current research scope does not authorize them).
- Whether publication may include observed results. No deployment or IE transfer is implied.

**Exit:** Explicit, scoped authorization. Founder intent to continue research is not the same as permission to run agents/CI or merge.

## 3. Acceptance/evidence object to ask the independent reviewer to approve

For every required test, the reviewer must define `test_case_id`, requirement revision, positive/negative kind, trusted fixture, expected behavior, whether mandatory, execution proof required, safety classification, and independently held result owner.

For every authorized attempt, evaluator must record:
- immutable base/candidate/evaluated Git source identifiers and cleanliness;
- suite/fixture/runtime/browser/DB digest;
- authenticated evaluator vs worker identity separation;
- actual required test counts and exits, not strings printed by app under test;
- both primary grade and noncompensable safety incident tags;
- all cost (model/hosting/QA/retries/human) and elapsed time, including incomplete/infra-error cases;
- status separately for candidate verified, integrated, staged, released, and beneficiary outcome.

A candidate success is not the same as an integrated or deployed success. This docket cannot designate PASS by itself.

## 4. Anti-claim and stop rules

A reviewer must STOP the attempt if the coder can edit hidden tests, source differs from verdict SHA, a required negative case has not run, current tool grant is absent, test environment could touch IE/Foromni production, or GitHub main is inadvertently writable by the candidate agent. Stop for unknown critical side effects until reconciled; never blind-retry a GitHub write after lost acknowledgment.
